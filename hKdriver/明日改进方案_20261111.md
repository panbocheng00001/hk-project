## 1. 多窗口：独立端口 + 独立 API 地址

### 问题根因

- `#inst=w2` 写在 URL hash 里，**跨域跳到 abs3 时整个 URL 被替换，hash 丢失**；
- 后台靠 `tabId→inst` 映射兜底，但映射是在 `onUpdated` 按 URL 解析的，那一刻 URL 已经没有 hash；
- 结果：`/config?who=` 收到空值 → 返回 `accounts[0]` → **w2 用的是 w1 的身份**。

### 方案：每个窗口一个本地端口

```
w1 → http://127.0.0.1:8765   （config 里第 1 人）
w2 → http://127.0.0.1:8766   （第 2 人）
w3 → http://127.0.0.1:8767
w4 → http://127.0.0.1:8768
```

扩展不再依赖 URL 传参，**API 端口本身就是身份**。

### 改动清单

| 文件 | 改法 |
|---|---|
| `ext_server.py` | `main()` 已支持 `--port`；新增 `--who w2`，把「端口 → 申请人」绑定写进服务实例内存，`/config` 忽略 `who` 参数，直接用实例绑定的那个人 |
| `extension/background.js` | `const API` 改为从 `chrome.storage.local` 读取（启动时由 content 首帧写入），读不到时回退 `8765` |
| `extension/content.js` | 首帧从 `location.search` 取 `?port=8766`，写入 `chrome.storage.local`；**用 search 而不是 hash**（search 在跳转时同样会丢，但只需要首帧取一次，之后靠 storage） |
| `launch_ext.ps1` | 新增 `-Port` 参数，URL 拼 `?port=8766`，并检查该端口服务是否在线 |
| `1_启动服务.bat` | 改成循环启动 4 个实例（8765–8768），每个窗口一份日志 |

### 验证方法

```powershell

foreach ($p in 8765,8766,8767,8768) {
  (Invoke-RestMethod "http://127.0.0.1:$p/config").applicant.name_cn
}
```

## 2. iframe 里的验证码：检测 + 自动拖

### 问题根因

`stageName()` 在主文档里找「拖动滑块」文字。滑块的 canvas 和文字都在 **Queue-it 的 iframe** 里，主文档 `innerText` 看不到。
（已加的 iframe 分支只做「按钮点击」，没做验证码识别。）

### 方案：iframe 内直接执行同一套滑块逻辑

`content.js` 的 `IS_FRAME` 分支里补充：

```
iframe 内 tick（1 秒一次）：
  1. 检测 canvas + 「拖动滑块」文字 → 上报 waf_captcha_frame（已做）
  2. 若有 canvas：toDataURL → POST /captcha → 拿 dx
  3. 在 iframe 内找滑块 handle → humanDrag(handle, dx * scale)
  4. 点 iframe 内的「提交」
  5. 3 次失败 → 上报 need_human（钉钉）
```

关键点：
- iframe 里 `canvas.toDataURL()` 不受跨域限制（canvas 内容同源绘制）；
- `pickHandle` / `humanDrag` 已在主文档实现，**抽成公共函数**，两处复用；
- iframe 尺寸小，`getBoundingClientRect()` 返回的是 iframe 内坐标，鼠标事件也在 iframe 内派发——一致，不需要换算到主文档。

### 验证方法

用本地 `http://127.0.0.1:8765/test_captcha_iframe`（**需要新增**）：
一个 iframe 里嵌入现有的 `test_captcha` 页面，确认：
1. 主文档无感知；
2. iframe 分支检测到验证码并上报；
3. 自动拖动执行；
4. `/captcha` 收到请求并返回 dx。

## 3. Queue-it 主动轮询：把 30 秒压到 1–2 秒

### 问题根因

放行信号来自 `POST /spa-api/queue/tdabsditest/{event}/{ticket}/`：
- `202` = 继续等
- `200` / `302` = 状态变化（可能是轮到你了）

这个轮询由 Queue-it 的 JS 控制，固定 **30 秒**一次。我们被动等它。

### 方案：Python 侧并行轮询，抢那 30 秒

前提：**必须拿到当前会话的 cookie**（今天的 `runs\cookies.txt` 就是模板）。

```
1. 扩展进到 abs4 排队页后，立即把 cookie 推给本地服务（新增 /cookies 调用点，
   现在只在 form 阶段推，要提前到 queue 阶段）
2. replay.py 新增 --watch-queue：
     · 从 cookies 或 netlog 里提取 ticket id
     · 每 1.5 秒 POST 一次 status
     · 一旦非 202 → 立刻响铃 + 钉钉 + 打印跳转 URL
3. 浏览器侧照常工作（它自己也会轮询），两边互不冲突
```

风险与验证：
- 高频轮询可能被 WAF 判异常 → 先用 1.5 秒试，观察是否出现 403/412；
- 若被拦，退回 5 秒；
- **不要用同一个 ticket 在两个客户端同时高频轮询**，先确认服务端不校验「单客户端」。

先验证一件事：用 `runs\cookies.txt` + ticket，从 Python 发一次 `POST`，看是否返回 202。
今天（11-10）没做，因为 w1 没开调试端口、cookie 只到 17:13 才有。
