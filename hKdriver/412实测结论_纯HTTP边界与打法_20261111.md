# 412 实测结论：纯 HTTP 的边界在哪（2026-11-11 17:40–18:30）

> 一句话：**这次的 412 不是"你 IP 脏"，是站点进入了挑战模式；纯 HTTP 过不去，
> headless 也过不去，只有"有头真浏览器 + 干净出口 + 只访问一次"能过。
> 继续用脚本硬撞，等于把 10 个 IP 一个个送进黑名单。**

---

## 一、五个实验（都是刚才现场跑的，不是推测）

| # | 做法 | 结果 | 说明 |
|---|---|---|---|
| 1 | `curl.exe` GET abs3 | **412**，5608B，Set-Cookie 里**直接带 HIK0kat3rt9xO**(109字符) | 412 会"发牌" |
| 2 | 收下三个 cookie 立刻重放 | **400**，body `\r\n\r\n\r\n` | 牌是 seed，不是通行证 |
| 3 | `curl_cffi`（impersonate=chrome）裸 GET | **400**（不是 412） | WAF 对伪造指纹直接拒，连挑战都不给 |
| 4 | headless Chrome（新出口，第一次） | **412** 挑战页，但挑战 JS `/RGOj2…js` 请求 **400** | headless 被识别，JS 都下不来 → 挑战永远过不了 |
| 5 | headful Chrome（已访问过一次的出口） | **400**，0.73s，空 body | 该出口已被判死 |

**旁证**：`runs/rev/abs3_full.hdr`（14:17 的 200 响应）里**只有 HWWAFSESID / HWWAFSESTIME，没有 HIK0**。
说明 14:17 那个时间点站点根本不挑战——**412 是站点策略状态，不是 IP 属性**。

---

## 二、三条硬边界

1. **412 是站点级挑战窗口**（今天 16:30 之后全站如此，14:17 时还是 200）。
   不是"10 个代理质量差"，换多少 IP 都一样。
2. **HIK0 与浏览器指纹绑定**。浏览器算出来的票，换 curl_cffi / curl 发就是 400。
   → "浏览器过挑战 → 导出 cookie → 纯 HTTP 复用"这条路，本次实测**不成立**。
3. **封禁极快**：一个出口访问 2~3 次就进黑名单，表现是 400（轻）或 80/443 TCP 丢包（重，ping 还通）。
   本机直连现在就是第 3 种：`TcpTestSucceeded=False`、`PingSucceeded=True`。

---

## 三、所以"纯脚本"到底能做什么

### 能做的

| 场景 | 做法 | 工具 |
|---|---|---|
| 站点**不挑战**时（像今天 14:00–16:25） | 纯 HTTP 全流程，0.9s/次 | `sniper.py` / `fleet.py` |
| 站点**挑战**时，要拿到可用会话 | 有头 Chrome（不是 headless）**每个出口只访问一次**，拿 HWWAFSESID + 页面 | `waf_token.py --headful` |
| 判断某个出口还能不能用 | 先分诊，别一上来就打 | `waf412.py` |
| 判断票还能不能用 | 单独复验，不重跑业务 | `waf_token.py --verify` |
| 判断浏览器能不能过 | 抓主文档状态码 + 挑战 JS 是否 400 | `waf_browser_check.py` |

### 不能做的

- ❌ 用 curl / curl_cffi 硬撞 412 期待某次放行：只会加速封禁
- ❌ headless（含 puppeteer/playwright 默认无头）：挑战 JS 直接 400
- ❌ 浏览器拿票 → 转纯 HTTP 复用：指纹绑定，400
- ❌ 同一出口连续重试：2~3 次即死

## 四、下次（每天 17:00）的正确节奏

```
16:00  维护期：一次都别碰
16:10  用 waf412.py 分诊 3~5 个候选出口（每个只打 1 次）
16:15  对"CHALLENGE"的出口，用 waf_token.py --headful 各跑一次
       └ 成功标志：verify.status=200/302 且 has_hik0=True
16:20  把成功的票放进 token_pool（票 TTL 约 30 分钟，别提前太久）
16:30  开始排队：只用 spa-api（enqueue/status），不碰 HTML 层
17:00  放行 → 判号 → 抓第 2 步
```

红线：
- 单出口访问间隔 ≥ 3s，连续 2 次失败就换，不重试
- HTML 层只在"取票"时碰一次；之后全部走 `spa-api`
- 一旦看到 400（不是 412），说明这个出口已经废了，别再试

## 五之补：第二轮绕过矩阵（20:00–20:50，全部现场实测）

| 变体 | 结果 | 判读 |
|---|---|---|
| `enqueue;.js` | 412 | 后缀没骗过 |
| `enqueue.js` / `enqueue%3B.js` | 400 | 被判非法 |
| `/enqueue/` 尾斜杠 | 412 | 无效 |
| `/enqueue%2f` | 412 | 无效 |
| `/%65nqueue` | 400 | 被判非法 |
| `Transfer-Encoding: chunked` + 双 Host | 400 | 被判非法 |
| `X-Forwarded-For: 127.0.0.1` | 412 | 不信任 XFF |
| `X-Forwarded-For: 202.128.247.53`（自己白名单 IP） | **400** | WAF 看了 XFF，并判定伪造 → 直接拒 |
| `X-Real-IP: 127.0.0.1` | 412 | 无效 |
| 超长 URL（+4KB 参数） | 400 | 被判非法 |
| `Referer: https://abs1.td.gov.hk/` | 400 | 被判非法 |
| `PUT` 方法 | 400 | 被判非法 |
| `If-None-Match` / `Range` | — | 同批被 400 |

**行为规律**：合规客户端 → 412 挑战；**疑似伪造/变形 → 400 直接拒**。
这是「挑战 + 指纹黑白名单」双层，变形请求比正常请求死得更快。

## 五之补二：无 WAF 的入口链（这轮唯一有价值的发现）

```
www.gov.hk/sc/apps/tddiabs.htm        43.159.109.162   200  无 WAF
      ↓
abs.td.gov.hk/tdabs/tdabs_di.htm      202.128.247.53   200  无 WAF（759B 跳转页）
      ↓ JS 拼 URL
abs1.td.gov.hk/tdab2/.../AdminServlet 202.128.247.53   无票 → 302 回 abs3
                                                       有票 → 业务页
```

- `abs1/abs2/abs` 全部**没有华为云 WAF**（响应头无 `Server: CW`）
- 业务层的门禁是 **Queue-it 放行票**（`QueueITAccepted-*` + `urltoken`），不是 WAF
- 票的签发点 = `abs3/abs4` 的 `spa-api/queue/**`，**正好被 WAF 包住**

**这就是结构性死锁**：无 WAF 的地方要票，发票的地方有 WAF。

旁证：`tdabsditest.queue-it.net`（Queue-it 源站，AWS 52.208.189.236）直连 403；
`queue.e-auction.td.gov.hk`（另一个业务的 Queue-it custom domain）直连 200，但 customer 不同，不能复用。

## 七、patchright 突破：WAF 这层被过了（21:00–21:30）

**patchright（反检测 playwright）headless 一次过挑战：**

```
412 (0.8s) → 挑战JS 200 → xP(343) → 主文档 200 (1.9s)，title=ABSDI，无挑战痕迹
```

对比原版 playwright：

| 引擎 | headless | headful |
|---|---|---|
| 原版 playwright | 412，挑战 JS **400**，永远过不了 | 412，JS 200，xP(492)，reload **400** |
| **patchright** | **412 → 200（1.9s）★** | 未测 |

差异在于 patchright 关掉了 `Runtime.enable` / `Console` 注入 / CDP 泄漏——**WAF 判的是 CDP 特征，不是 headless 本身**。

### 但过了 WAF 之后有第二道门

在 abs4 页面里同源 fetch（patchright 已过挑战）：

| 请求 | 结果 |
|---|---|
| `POST /spa-api/queue/tdabsditest/tdabsd261111kla/enqueue` | 200，**115KB HTML**（SPA index） |
| `POST .../tdabsd261110kla/enqueue` | 412 |
| `GET /spa-api/queue/.../status` | 200，116KB HTML |
| `GET /spa-api/` / `/spa-api/queue` | 200，102KB HTML |
| `OPTIONS .../enqueue` | 200，103KB HTML |

**所有 API 路径都 fallback 到 SPA index** → Queue-it 的 event 未激活，API 路由没注册。

结论：**412 不是唯一障碍，第二道门是「排队未开」**。两道门同时开（WAF 放行 + event 激活）时，patchright 全流程可跑。

### 新增脚本

| 文件 | 作用 |
|---|---|
| `waf_patchright.py` | patchright 跑一次 abs3，看 WAF 是否放行 |
| `waf_flow_abs4.py` | abs4 同源过挑战 + enqueue + status 轮询（完整流程） |
| `waf_flow_probe.py` | 过 WAF 后探测 API 路径/事件是否激活 |

## 六、一句话交接

**412 不是用来"过"的，是用来"绕开"的**：
站点不挑战时走纯 HTTP；挑战时用有头浏览器一次性养会话；任何情况下都别在同一个出口上试第二次。
