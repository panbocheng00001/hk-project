# 验证码取证与离线复刻（2026-11-11）

> 目标：**现场过不去也不耽误事**——先把原始数据、接口、签名、token 全存下来，离线再解；
> 再用本地靶场复刻同样的题给求解器练，避免"只在正式开闸那一分钟试一次"。
>
> 两个新工具：
> - `runs/rev/captcha_forensics.py` —— **取证采集器**（挂浏览器上，自动记录，不注入不改页面）
> - `runs/rev/captcha_mock.py` —— **本地靶场**（出同样的题、同样的接口、发同样的 token）

## 一、这套系统里会出现的三类验证码（别混）

| # | 类型 | 出现位置 | 谁校验 | 现场难度 |
|---|---|---|---|---|
| 1 | **华为 WAF 行为验证**（canvas 图形配对，拖滑块） | `abs3`／`abs4` 的 412 挑战页、`abs3/SelectCountry` 之后 | WAF 自己（写 `HIK0kat3rt9xO` cookie + 动态参数） | 中：`extension/captcha_solver.js` 已能自动解（离线自测 20/20） |
| 2 | **MTCaptcha** | 第 1 步表单页的 `#captchaToken`；第 4 步递交 | 业务后端（`captchaToken` 随表单提交） | 高：图片点选做不干净；但**第 1 步实测留空也能提交**（先判名额） |
| 3 | **Queue-it 自己的 challenge** | `abs4` 的 `enqueue`/排队页（`challengeRequired`） | Queue-it | 低：实测一直是 `false` |

**关键实测结论（11-11 14:33）**：第 1 步 `captchaToken` 留空提交，服务端照常回答「有没有名额」+ 发 `TrackId`。
所以「无浏览器判号」这条路**不需要过验证码**；真正需要 token 的是**第 4 步递交**。

## 二、取证采集器：`runs/rev/captcha_forensics.py`

### 它抓什么

| 层 | 内容 |
|---|---|
| 网络 | 所有 host 含 `mtcaptcha` / url 含 `captcha` / `queue-it` 的 **request + response**：完整 URL、method、请求头、POST body、响应头、响应体 |
| 页面 | 每个 iframe 的 DOM 片段（含 captcha 字样的元素）、每个 `canvas.toDataURL()` 原图、`input[name*=captcha]` 的值（**这就是 token**） |
| 全局 | `window.MTCaptcha` / `MTCaptchaConfig` / `QueueIt` 等对象的键名结构 |
| 落盘 | `bodies/<sha1>.<ext>` 去重存原文；图片直接存 `.png/.jpg`，JS/JSON 存原文件 |

### 怎么用

```powershell
# 挂着采（默认 12 分钟，每 3 秒一帧快照）
python runs\rev\captcha_forensics.py --minutes 40

# 抓到非空 captchaToken 就收工
python runs\rev\captcha_forensics.py --minutes 40 --stop-when-token
```

产物目录：

```
runs/captcha/<YYYYmmdd-HHMMSS>/
    requests.jsonl       每条请求/响应一行（JSON，含 header 与 body 引用）
    bodies/<sha1>.*      响应体原文（题目图 / SDK js / challenge JSON）
    snapshots/0001.json  页面层快照（DOM 片段 + canvas + captchaToken + 全局对象键名）
    snapshots/0001_canvas0_<hash>.png   画布原图
    captcha_token.txt    抓到就写这里（原文，方便直接拿去重放）
    README.txt           本次采集说明
```

### 现场怎么排

```
1) 排队放行 → 一进第 1 步页面就开采集器（别等验证码弹出来）
2) 人手动过验证（能过就过，过不了就停那儿，采集器一直在记）
3) 抓到 token → captcha_token.txt 有内容 → --stop-when-token 自动收工
4) 事后用 requests.jsonl 复盘：challenge 请求长什么样、token 怎么来的
```

> 采集器**只监听**：不注入脚本、不改函数、不点页面。所以不会像 Playwright 那样把 WAF 惹毛。

## 三、本地靶场：`runs/rev/captcha_mock.py`

复刻两种题面与接口，用来把求解器调稳（不是替你过线上验证码）。

```powershell
python runs\rev\captcha_mock.py --port 8790
# 浏览器打开 http://127.0.0.1:8790/test  （左右两个按钮：图片点选 / 滑块配对）
```

接口（**路径与字段对齐 MTCaptcha 公开形态**）：

```
GET  /mtcv1/api/getchallenge.json?sitekey=sk-test&kind=pick|slider
  → {"success":true,"challengeId":"…","challenge":{"type":"pick|slider",
     "image":"data:image/png;base64,…","prompt":"…","grid":3|"trackW":400},
     "ttl":180,"sitekey":"sk-test"}

POST /mtcv1/api/checkcaptcha.json   {"challengeId":"…","answer":"5,4,3" | "159"}
  → {"success":true,"token":"<base64url 长串>","ttl":300}
  → {"success":false,"error":"wrong_answer"} / {"error":"challenge_not_found"}
```

题型说明：

| 题型 | 生成方式 | 对应线上的什么 |
|---|---|---|
| `slider` | 深色网格背景 + 一个**空心形状缺口** + 一个**实心同形手柄** + 同尺寸异形干扰块 | 华为 WAF 行为验证（`captcha_solver.js` 就是解这个） |
| `pick` | 3×3 网格，3 个格子放彩色目标图形，其余是灰色干扰圆 | MTCaptcha 的图片点选题（顺序敏感） |

自测（进程内出题→取答案→校验→拿 token）：

```powershell
python runs\rev\mock_selftest.py
# [pick]   id=… img=9582B  answer=5,4,3   verify → success=True token=ZCHk3dvd…
# [slider] id=… img=3886B  answer=159     verify → success=True token=E3nWlRVA…
```

每次请求/响应也落 `runs/captcha_mock/requests.jsonl`，方便和真样本逐字段对比。

## 四、离线分析路线（拿到采集包之后）

```
① 打开 runs/captcha/<ts>/requests.jsonl
   找 host = service.mtcaptcha.com 的那几条：
     getchallenge.json      ← 题目 + challengeId + sitekey
     getimage / getaudio    ← 题目图（如果走独立图片接口）
     checkcaptcha.json      ← 提交答案 + 返回 token
② 对应响应体在 bodies/<sha1>.js｜.json｜.png
   · .js   → 就是 MTCaptcha SDK，签名/sitekey 生成逻辑在这里面
   · .json → challenge 的完整结构（字段名、ttl、难度参数）
   · .png  → 题面原图，直接进求解器
③ 在 snapshots/*.json 里找
   · tokens.captchaToken.value   ← 最终 token（重放/对照用）
   · globals.MTCaptchaConfig     ← sitekey、语言、回调名
   · dom_hits[]                  ← 含 captcha 的 iframe/script/DOM
④ 把 ② 的字段名回填到 captcha_mock.py 的响应结构里
   → mock 就和线上"长得一样"了，求解器可以对着它反复跑
```

## 六、脚本怎么知道「撞到验证码了」（2026-11-11 新增哨兵）

纯 HTTP 没有浏览器，所以最怕的是**静默卡住**。现在不会了——`sniper.py` 有三个检测点：

| 检测点 | 位置 | 触发条件 |
|---|---|---|
| `S5 enter` | 进业务页之后 | 响应里出现可交互验证码元素 |
| `S6 step1` | 判号前 GET + 提交后 POST | 同上，或服务端回「验证码错误/已过期」 |
| `S7 booking` | 名额概览页 | 同上 |

**判据（刻意避开误报）**：

```
算「有验证码」：<script src="…mtcaptcha…">  /  class="mtcaptcha"  /  data-sitekey
              hcaptcha.com/1/api.js  /  recaptcha/api.js  /  challenges.cloudflare.com/turnstile
              「请拖动滑块」「請拖動」
              「驗證碼錯誤/不正確/已過期」「captcha required|invalid|expired」
不算：CSP 头里的 service.mtcaptcha.com —— 第 1 步页面一直有那一行，按字符串匹配会天天误报
```

自测 7/7 正确：

```
CSP 里的域名（应判无）                 -> （无）        ← 关键：不误报
真实 mtcaptcha script                 -> mtcaptcha
sitekey 元素                          -> mtcaptcha
服务端拒绝                             -> rejected
hcaptcha                              -> hcaptcha
滑块文案                               -> waf_slider
普通第 1 步页面（应判无）               -> （无）
```

**命中之后做什么（关键：不是重试，是停手）**：

1. 证据落盘：`runs/sniper/captcha-<阶段>-<时间>.html`
2. 写告警文件：`runs/sniper/ALERT.md`、`runs/fleet/ALERT.md`
3. 推钉钉（走项目已有的 `notifier.captcha_need_human()`）
4. 该 worker **立刻停手**（返回 44），不再撞——`waf.py` 的结论是「越试越进不去」
5. 日志里直接打出三条兜底路径

**它不会卡死的保障**：

| 层 | 机制 |
|---|---|
| 每个请求 | `timeout=25s` + 失败重试 1 次（代理首包 502 常见） |
| 每次 status 轮询 | 连续 3 次失败即退出该 worker |
| 每个 worker | 有 `deadline`（默认 17:40），到点自己退 |
| 主控 | `while any(t.is_alive())` + `business_done` 双条件退出 |
| 验证码 | 检测到即停，不进重试循环 |

**但要说清楚物理限制**：纯 HTTP **产不出** `captchaToken`——
它不是算出来的，是 MTCaptcha 服务端在「你答对题」之后签发的。
所以撞到验证码只有三条真路：

| 优先级 | 做法 | 代价 |
|---|---|---|
| 1 | 把该会话 cookie 交给浏览器（`runs/fleet/winner_cookies.json`）→ 人过验证 → 导回 | 需要人在场 30 秒 |
| 2 | MTCaptcha 打码平台（`sitekey` + `pageurl` 换 token） | 要账号、要钱 |
| 3 | 先空着 `captchaToken` 提交一次（**第 1 步实测能过**） | 免费，但只对第 1 步有效 |

> 实测依据：11-11 14:33，`captchaToken` 留空提交，服务端照常返回「没有可供预约的时段」+ `TrackId`。
> 所以 IP-01~07 纯 HTTP 跑判号这一段，**大概率根本不会遇到验证码**。

## 七、自动救援：撞到验证码 → 脚本自己开浏览器，你只拖一下（已实现）

`captcha_rescue.py` + `sniper.py --auto-rescue` 把「人工过验证」压成一次拖拽：

```
① 起独立 Chrome for Testing（端口 9223，profile runs/rescue_profile，不碰你日常窗口）
② 把当前 HTTP 会话的 cookie 灌进去（会话不丢，不用重新排队）
③ 直接导航到刚出验证码的那个页面
④ 你在窗口里拖一下滑块 / 点几下
⑤ 脚本轮询到 captchaToken 有值（或页面跳到下一步）→ 自动导出 cookie
⑥ 自动回灌进 HTTP 会话，从刚才失败的那一步继续跑 —— 你不用回来敲任何键
```

### 两种用法

```powershell
# A) 自动：撞到验证码时 sniper 自己调救援（推荐，fleet 里默认开启）
python sniper.py --cookies runs\rev\browser_cookies.json --step1 --auto-rescue
python fleet.py --link "<链接>" --start-at 16:30:00 --workers 10        # 默认 --auto-rescue 开启

# B) 手动：给 URL + 刚导出的 cookie，救援完拿 runs/rescue/rescue_out.json
python captcha_rescue.py --url "https://abs1.td.gov.hk/...AdminServlet?cmd=..." `
                         --cookies runs\sniper\rescue_in.json
```

### 触发点与行为

| 位置 | 传给救援浏览器的 URL | 救援成功后 |
|---|---|---|
| S5 进业务 | Queue-it 的 `t=` 目标 | 重跑 `enter()` |
| S6 判号（GET） | 第 1 步入口 | 重跑 `step1()` |
| S6 判号（POST） | 第 1 步入口 | 重跑 `step1()`（带上新 token） |
| S7 名额概览 | 概览接口 | 重跑 `booking_status()` |

保护：**同一个 Sniper 最多自动救援 2 次**（防止在"永远过不去"的页面上打转），
超过就停手并写 `ALERT.md`。

### 实测（冒烟，15:48）

```
已启动救援浏览器（端口 9223，profile rescue_profile）
导航 → https://abs3.td.gov.hk/?lang=sc
  … ABSDI token=0 url=https://abs3.td.gov.hk/?lang=sc
导出 3 条 cookie → runs\rescue\rescue_out.json
RESCUE_OK
```

浏览器起得来、cookie 灌得进、导航正常、轮询正常、cookie 导得出。
真验证码出现时，第 ④ 步就是你需要动手的那 10 秒。

## 八、一句话交接

- **先采后解**：`captcha_forensics.py` 挂着，什么都不用管，验证码一出现全套原始数据就落盘了。
- **要练先造题**：`captcha_mock.py` 出的是同结构、同接口、同 token 形态的题，求解器在这里调稳再上线上。
- **别指望一次过**：第 1 步实测不需要 token，真正要 token 的是第 4 步递交——所以采集窗口应该覆盖「递交那一次」，而不只是第 1 步。
