# 纯脚本跑通全流程（不调起浏览器）：方案与可行性判定

> 日期：2026-11-12 · 依据：今天 16:32 的取票实测 + 本次离线复放（零目标流量）
>
> **一句话结论：可行，但"不调起浏览器"要付的代价是"自己当一次浏览器内核"。
> 这件事已经从"不可解"降级成"可枚举的注入点清单"——今天把挑战 VM 拆到能执行、
> 能自我 eval、只剩宿主能力对齐；剩下的是 1~3 人日的离线迭代 + 1 次真样本校验。
> 如果目标只是"脚本跑、不弹窗、不用手点"，那 `patchright --headless` 今天就能跑完，
> 两者差别只在于"要不要多一个 300MB 的隐藏进程"。**

| 段 | 内容 | 现状 | 纯脚本可行性 |
|---|---|---|---|

C 是唯一还没拿下的。它不是"整条链都要浏览器"，而是**一次取票要不要浏览器**。

## 二、C 段的真实约束（决定方案形态，不是拍脑袋）

### 2.1 票与出口三元组绑定

今天 16:32 实测（挑战窗口内）：

```
弱票（只有 HWWAFSESID，站点不挑战） → curl_cffi chrome136 → 200   ✅
硬票（HIK0kat3rt9xO，过了挑战）     → chrome136/131/默认 全 400    ❌
```

11-11 22:45 的 `mint_align → align_client --verify` 两个出口都是 200，但那张票**没有 HIK0**——
两批实验合起来的读法是：**绑的不是"浏览器"，是"票 + 出口 IP + 该会话的 TLS/UA 画像"**。
推论（这条决定工程形态）：

> 挑战必须和后续请求在**同一个 HTTP 客户端、同一套指纹**里完成。
> 不能"浏览器铸票 → curl 复用"，也不能"curl 取种子 → 换个画像装 cookie"。

### 2.2 挑战脚本不是黑盒，是**栈式 VM**（今天第一次拆开）

对 `runs/rev/abs3_waf_js.js`（304,473 字符）的静态与动态分析：

| 特征 | 观测 | 含义 |
|---|---|---|
| 结构 | 操作码数组 + `while(1)` 派发（`_$ct` / `_$pB` / `_$$D`） | 是自研 VM，不是普通混淆 |
| 是否二次生成 | **是**：运行时 `eval()` 出 493,217 字符的分发器（已落盘 `wafnode/_gen/gen_001.js`） | 想静态还原 = 反编译一个 VM |
| WebAssembly | **0 处** | 不用 WASM，纯 JS 可跑 |
| canvas / WebGL / getImageData / toDataURL | **0 处** | 不做渲染指纹 |
| navigator / screen / plugins | **0 处**（按名字查） | 不做 UA/分辨率指纹枚举 |
| 实际读的宿主能力 | `window`、`document.cookie`、`getElementsByTagName('base')`、`Math`、`Date`、`unescape`、`String.fromCharCode/charCodeAt` | **注入面很小，可枚举** |
| 反调试 | 生成代码里有 `debugger` 指令（VM 的 opcode 104） | Node 下是空操作，不影响 |

对照 `waf_solve.js` 那次 4 GB OOM：**失败的原因是方法错**（万能 Proxy stub + 直接 `vm.runInContext`），
不是"不可解"。今天的做法是给它一个**有真实语义的最小宿主**，而不是"骗"它。

### 2.3 今天把失败点推进到了哪（零目标流量，全部本地）

| 里程碑 | 做法 | 结果 |
|---|---|---|
| M1 | 用 `fresh412.html` 里的 `nsd/cd` 喂真挑战 JS | 顶层执行到一半：`$_ts` 长出 `cp/jf/aebi/scj` + 操作码名表，说明**种子被正确消费** |
| M2 | 未插桩 | `TypeError: _$oN[_$al] is not a function`（VM 调了一个不存在的宿主函数） |
| M3 | 钩 `eval` 记录生成代码 + 在调用点插桩 | 缺的能力被点名；换成"稀疏 DOM"时错误变成 `String.prototype.charCodeAt called on null or undefined` → 说明它**确实读了页面元素**，走了另一条分支 |
| M4 | 补齐 `getElementsByTagName/script/base` 等 | 回到"缺函数"，且插桩点 `missing=[]` → 缺的不是方法，是**某个它期望从环境拿到的字符串值是 undefined** |

也就是说：**问题从"猜它要什么"变成了"按报错补一个具体值"**。这是可收敛的形态，不是死路。

## 三、三条路线（按"是否真的零浏览器"排序）

### L1 —— 真·零浏览器：Node 跑挑战 VM + curl_cffi 固定画像（推荐做主线）

```
curl_cffi(chrome136)  ──① GET abs3 ──► 412 + $_ts{nsd,cd} + /RGOj2…/x.js
        │  （同一个 Session，全程不换画像）
        ├─② GET 挑战 JS（Referer 同源）
        ├─③ node wafnode/solve.js  →  document.cookie（HIK0…）
        ├─④ 同 Session 装 cookie → 再 GET abs3 → 200/302
        └─⑤ 票落盘 → sniper.py --align 走 A/B/D 段
```

- 已落地的件：`wafnode/shim.js`（最小宿主 + 全量记录）、`wafnode/run412.js`（离线复放）、
  `wafnode/solve.js`（stdin/stdout 契约）、`mint_pure.py`（五段接线 + 退出码）
- 还差的：`solve.js` 要把"最后一个 undefined"补齐，产出 cookie。**离线迭代，零目标流量。**
- 收益：单票 <300ms、无进程、可横向几十并发；WAF 升级只需重跑一次复放。
- 代价：VM 是"每站一版"的，站点换挑战版本就重做一轮（1~3 h）。

### L1' —— 折中：Node 只当"token 服务"，HTTP 全走 curl_cffi

与 L1 同构，差别是 solve.js 常驻、预热 JIT，主进程随时问它要 token。
适合"多出口并发取票"（每出口一个 Session，token 由同一个 worker 算）。

### L2 —— 无窗口内核：patchright headless 当取票器（今天就能跑）

- 已实测：`412 → 挑战 JS 200 → xP(343) → 主文档 200，1.9s`，全程无窗口
- 形态：`r2_flow.py` 已经是"同上下文跑完 enqueue/status/业务页"，缺的只是接成状态机
- 代价：300–400MB/实例；收益：**不依赖任何逆推**，WAF 升级也不怕

> 如果"不需要调起浏览器"= 不弹窗、不用手点，**L2 现在就能交付**；
> 如果 = 连 chromium 进程都不许有，**才需要 L1**。

### 已排除

- ❌ 纯 HTTP 硬撞 412（只会把出口打进黑名单，2~3 次即死）
- ❌ "浏览器铸票 → 导出 cookie → curl 复用"（16:32 实测全 400）
- ❌ 拿来就 `vm.runInContext` + 万能 Proxy（4GB OOM 的那条）

## 五、红线（写进流程，不是建议）

1. 单出口 ≥3s 间隔；同一出口连续 2 次失败即弃；见到 400 立刻判死（**别重试**）
2. HTML 层只在取票时碰一次；排队全走 `spa-api`
3. 一张票只配一个出口；票与出口 IP 绑定，换 IP 立即作废
4. 票 TTL ≈30min（实测 25min 起提醒），`nsd/cd` 是**一次性种子**，不能跨响应复用
5. 16:00 维护期一次都别碰；16:30 之后才是挑战窗口

## 六、成本 / 收益 / 风险对比

| | L1 纯脚本 | L1' token 服务 | L2 无窗口内核 |
|---|---|---|---|
| 是否起 chromium | 否 | 否 | 是（隐藏） |
| 单票耗时 | <300ms | <300ms（JIT 热） | 1.9–3.5s |
| 内存 | ~60MB/进程 | ~60MB | 300–400MB/实例 |
| 工期 | 1–3 人日（M1 为主） | +0.5 人日 | 0（已有） |
| 抗 WAF 升级 | 中（要重跑复放） | 中 | 高 |
| 横向并发 | 高（进程轻） | 高 | 低（内存墙） |
| 主要风险 | VM 版本变更；最后一个 undefined 可能牵出新的依赖 | 同左 | 指纹/Cdp 特征（patchright 已过） |

**建议**：主线走 L1（M1 离线推进，不烧出口），L2 作为"明天就要用"的兜底——
两条路共用 `mint_pure.py` 的票格式，切换只改一个 `--engine`。

# 3) 出口还有配额就复验一次（+1 次请求）

| 现象 | 含义 | 下一步 |

| 步骤 2 出 `HIK0kat3rt9x*` | VM 侧成立 | 进 M3，接 `sniper --align` |

| 分诊 | `curl -x … abs3/?lang=sc` | **200 708B**，只有 `HWWAFSESID/TIME`，**无 HIK0 → 站点此刻不挑战** |
| 全链 A/B | `python sniper.py --probe --proxy …` | ① 200 → ② `c=tdabsditest e=tdabsd261112eoy` → ③ `enqueue 200 queueId=34f9916d… challengeRequired=False` → ④ `state=2 forecast=InLine→FirstInLine`，eta 后滑 |
| 驱动脚本 | `python go1630.py --dry` | 新出口 `175.6.31.237:39097` → 200 708B，链路可用 |

两个当场修掉的坑：

1. **curl_cffi 过这些出口报 `SSL certificate: unable to get local issuer`** —— `curl.exe` 同出口却正常，说明是 curl_cffi 的 CA 链问题，不是代理 MITM。已按 `sniper.py` 同口径改成 `verify=False, trust_env=False`（`go1630.py` / `mint_pure.py`）。
2. 短时间连续调 `getips` 会**返回同一个 IP**（`filter=1` 去重），驱动里已按"换到不同地址才算新出口"处理。

结论：**A/B 段现在就能纯脚本跑通；C 段取决于站点是否在挑战窗口（今天 14:18 不在）；D 段仍卡在 Queue-it 放行票**。

## 七之补二：2026-11-13 16:30–17:13 现场（挑战窗口内）

### 关键突破：挑战**确实能过**，令牌是 492 字符那一档

17:11，用一条**从未被碰过**的新出口（`222.216.120.151:48909`），让浏览器做**第一个请求**：

```
17:11:10  ① 首包 412
17:11:10  ① 等待中 bodyLen=0 HIK0={'HIK0kat3rt9xO': 109}      ← 109 是种子，不是票
17:11:17  ① 挑战完成 HIK0={'HIK0kat3rt9xO': 109,
                          'HIK0kat3rt9xP': 492}   11.1s       ← 真令牌
17:11:20  ② SelectCountry → status=400，正文空（reload×2 仍空）
```

### 三条硬规则（今天用真金白银换来的）

1. **绝对不要用 curl 做预检。** 预检会吃掉该出口的"首请求额度"，浏览器随后必然 400。
   今天多次 400 都是这么来的：curl 拿 412 → 同 IP 上浏览器 → 400。
2. **HIK0 出现 ≠ 挑战完成。** 400/412 页面本身会发一枚 109 字符的种子。
   判据只认：`HIK0kat3rt9x*` 的 value 长度 ≥ 200（实测 343 / 492 两档）。
3. **每个出口只够 1–2 次请求。** 第三次开始稳定 400；直连（本机宽带 IP）已是 TCP 丢包。

### 当前唯一未定项：第二跳 400 的成因

两种可能，单变量可区分：

| 假设 | 判别方法 |
|---|---|
| A. 我加的"掐资源"（`route.abort` 图片/字体/CSS）干扰了挑战完成握手 | 用 `--no-block` 重跑同一条链路 |
| B. 令牌与**首条连接**绑定，新连接必被重挑战 | 同一条连接上先 reload 同一 URL，看是否 200 |

对应命令（明天出口就绪后，第一条就够）：

```powershell
python r2_flow.py --proxy http://IP:PORT --no-block --minutes 35 --ip-id q1
```

### 出口侧现状

- 巨量账户：`资源包余额不足，请购买新资源包!` —— 17:12 起已取不到 IP
- 历史 14 个 IP 全部过期；直连 TCP 被丢包（本机公网 IP 已被拉黑）
- 结论：**这不是脚本能解决的问题，必须先补出口**
