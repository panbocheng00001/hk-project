# 验证码自动识别 / 自动通过：改了什么

> 2026-11-10 22:20–22:45 实测。你今天遇到的是「验证码弹出来、脚本一动不动、只能自己拖」。
> 根因不是算法不行，是**三段接线断了**。下面按「为什么会静默 → 改了什么 → 怎么验」写。

---

## 一、为什么它会一动不动（三个真原因）

| # | 原因 | 证据 |
|---|---|---|
| 1 | **iframe 里根本没有脚本**。`background.js` 只在 `tabs.onUpdated`（主文档完成）注入一次，iframe 是之后才创建/加载的，那一份永远进不去 | 加诊断后：注入主文档有日志，iframe 一条都没有 |
| 2 | **就算注入了也只看不解**。`content.js` 的 `IS_FRAME` 分支只发一句「⚠ iframe 内出现验证码（请手动完成）」 | 代码原样如此，2026-11-10 的部署日志能看到这句 |
| 3 | **MTCaptcha 只观察不动**。`doMTCaptcha()` 只存档上报，从不点击 | 同上 |

第 1 条最关键：**Queue-it / WAF 的验证码是动态 iframe**，正是这个形态让脚本「看着在跑、实际什么都没做」。
所以你手动过的那一次，等于替它干了它根本没在干的活。

## 二、改了什么（6 处，都在 `extension/`）

| 文件 | 改动 | 作用 |
|---|---|---|
| `captcha_solver.js` | **新增**（约 560 行） | 通用求解器：盘点 → 分类 → 求 dx → 拖动 → 复核。主文档、iframe、Shadow DOM 都跑一份 |
| `background.js` | 注入顺序 `captcha_solver.js → content.js`；新增 `webNavigation` 子帧补注入；新增 `trustedDrag`（chrome.debugger） | 迟到的 iframe 也能拿到脚本；合成事件被拒时可升级成可信输入 |
| `background.js` | `TARGET_RE` 加 `mtcaptcha.com/.net` | MTCaptcha 自己的 iframe 也能被注入 |
| `content.js` | 主文档 `doWafCaptcha` 改为调 `__CAPSOLVER.solve()` | 识别/求值/拖动统一走求解器，保留旧路径兜底 |
| `content.js` | iframe 分支：**发现就解**（原来只上报），并加 `frame_init` 自检 | iframe 内不再等人工 |
| `manifest.json` | 加 `debugger`、`webNavigation` 权限；`content_scripts` 声明 `all_frames + document_start` | 双保险：声明式注入 + 程序式注入 |

## 三、识别与求解的逻辑

### 分类（`scan()`）
按 DOM 特征判型，顺序即优先级：

```
canvas + "拖动滑块/重合/实心空心"      → waf_slider      ← 华为行为验证
canvas + 可拾取手柄                    → waf_slider
iframe[src*=mtcaptcha] / [class*=mtcap] → mtcaptcha
"请依次点击/点选" + canvas              → click_select    （未内置，上报）
turnstile / hcaptcha / recaptcha bframe → 对应类型（点一下 + 上报）
img[src*=captcha]                      → image_code      （未内置，上报）
```

### 滑块求 dx（`computeDx()`，纯 JS，不依赖 Python/OpenCV）
1. `getImageData` 取位图；
2. **三档阈值**排掉深色网格（严格档 `sat>90 && val>90`，逐级放宽）——网格线不排掉会把所有形状连成一坨，这是第一版失败的原因；
3. 连通域（显式栈 BFS，不吃栈内存）；
4. 按**填充密度**分「实心 / 空心」；
5. **形状剖面配对**：把每块外接框切成 8×8 格算占用剖面，空心块先「填满」（从外接框边界 BFS 找外部，剩下的空腔即内部）再比剖面 —— 判据是「形状相同」，不是「外接框大小接近」。干扰图形经常尺寸也接近，只有形状对不上；
6. 打分 = 尺寸差 + 高度差 + 色相差 + 形状距离×1.8；
7. 主色簇里**重算一遍**（把不同色的干扰像素剔掉，外接框回正）。

### 拖动
- 位图像素 → 轨道行程：`dx × (轨道宽 - 手柄宽) / 位图宽`；
- 轨迹：先移入→悬停→按下→停顿→加速/匀速/减速→微抖→末端过冲回拉→停顿→松手；
- **两条路**：先合成 `PointerEvent`（无痕）；重试时升级 `chrome.debugger` 的 `Input.dispatchMouseEvent`（`isTrusted=true`，不需要开 `--remote-debugging-port`）。代价是标签页顶部一条「正在调试」提示条，不想要就设 `localStorage.tdabs_trusted_input = "0"`。

## 四、验证结果（都是实测，不是估计）

**离线合成题**（`python captcha_selftest.py --n 20`，题目按实测截图的样子生成：深色网格 + 实心/空心同类图形 + 干扰块）：

```
分类       1/1
求 dx      20/20   误差均值 0.23px  最大 0.76px
拖动       20/20
结论： 全部通过

难题（同尺寸干扰 + 异色配对）: dx=180.0 真值 180 差 0.0px
拖动换算：位移 164.7px 期望 164.7px 差 0.0px
```

**真扩展链路**（`python ext_integration_test.py`，CfT 加载扩展打开本地合成题 + iframe 版）：

```
bg_init            SW 启动 webNavigation=true debugger=true
bg_inject          主文档注入 ok /test_captcha
waf_captcha        ⚠ 出现验证码（滑块（文案+canvas）），自动求解中
frame_init         iframe 注入：/test_captcha | solver=有
bg_frame           帧注入 tab=… frame=9 成功
waf_captcha_frame  ⚠ iframe 内发现验证码（滑块（文案+canvas）），本帧开始自动求解
waf_captcha_frame  js dx=180.0 → 178.2px(synthetic) ; js dx=180.0 → 187.1px(debugger)
```

主文档和 iframe 都算出了 dx=180.0（真值 180），拖动两条路都执行了。
「未过」是题目本身不消失（测试页没有成功回调），不是求解失败。
`178.2px` 与理论 `164.7px` 的差来自测试页 canvas 400px、轨道 430px 不一致 —— 真实页面两者同宽，不会有这个差。

## 五、今晚怎么用（两步，别忘第 2 步）

```powershell
# 1) 起服务（新版已重启，接口含 /test_captcha_frame）
python ext_server.py --port 8765 --who w1     # 或 1_启动服务.bat

# 2) 关键：--load-extension 会把 extension/ **复制**进 profile，源目录改了不会自动同步。
#    必须删掉旧 profile，否则跑的还是昨天那份脚本。
Remove-Item .\chrome_ext_w1 -Recurse -Force -EA SilentlyContinue
powershell -ExecutionPolicy Bypass -File .\launch_ext.ps1 -Instance w1
```

判断有没有生效，看 `runs/ext_status.jsonl` 新增的三类行：

```
frame_init          沙箱注入自检（id 帧也在内，solver=有）
waf_captcha_frame   iframe 内发现验证码 → 本帧开始自动求解
captcha_solved      ✅ 已自动通过
```

只要看到 `frame_init` 里 `solver=有` + `waf_captcha_frame` 后面的 `dx=…`，就说明它真的在动手了。
