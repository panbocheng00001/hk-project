# 16:30 十 IP 作战编排（2026-11-11）

> 一条命令把 10 个代理 IP 分工派活，谁拿到门票谁跑完后续流程。
> 编排器：`fleet.py`（已用 3 worker 演练通过，见文末「演练记录」）

---

## 一、角色分配（10 个 IP）

| IP | 角色 | 干什么 | 为什么 |
|---|---|---|---|
| **IP-01 ~ IP-07** | `queue` 排队组 | 各自 `WAF → enqueue → 轮询 status`，等自己那条被放行 | 17:00 是**随机洗牌**，多一条 ticket 就多一分概率 |
| **IP-08** | `probe` 探号组 | 不排队；winner 出现后立刻用**winner 的 cookie** 高频查 `booking_status` | 判号只要 0.9 秒（代理），探测次数直接决定抢到概率 |
| **IP-09** | `verify` 验证机 | **不抢号**，按轮跑 `verify_flow.run_once()` 的 S1~S7 自检，每轮落一份报告 | 留一台专门回答「脚本现在还行不行」；哪一步退化了当场发现，而不是等开闸时才发现 |
| **IP-10** | `reserve` 兜底组 | 保留不动，winner 掉线/被封时顶上 | 20 分钟窗口，出一次意外就报废 |

**第一个 `released` 的排队 worker = winner**，它自己继续往下跑（同一 IP、同一会话，最稳）：

```
enter（进业务页）→ step1（判号）→ 有名额 → 抓第 2 步页面落盘 → 通知交接
```

验证机（IP-09）的产出：

```
runs/fleet/verify_IP-09_01.json   第一轮 S1~S7 明细（PASS/FAIL/SKIP + 耗时 + 证据）
runs/fleet/verify_IP-09_02.json   第二轮 …
fleet.log 里一行：[IP-09] 验证第 1 轮 exit=42 全通
```

> 为什么 winner 用自己 IP 跑：实测 cookie 跨 IP 可用，但**同 IP 同会话**是最不容易出意外的组合。

## 五、失败矩阵

| 现象 | 判定 | 处理 |
|---|---|---|
| 某条 worker `WAF 层失败` | 该 IP 被判异常 | 自动重试 3 次；仍失败就退出排队，不影响其他条 |
| 全部 `forecast=FirstInLine` 但无 `redirectUrl` | event 不开闸（今天 14:52 实测 171 次就是这样） | 说明当天这个 event 不会放行 → 只能等官方真正开闸 |
| `enqueue` 返回 400 | eventId 变了 | `fleet.py` 启动时会重新 discover，不用手改 |
| winner 出现但 `enter` 失败 | 放行票没落到会话里 | 用 `winner_cookies.json` 重试一次；仍失败就让 IP-10 顶上 |
| 代理 407 / 502 | 动态代理过期 | 重提即可（`--link` 再跑一次） |

## 七、红线（编排层面）

1. **不改 `num`**：提代理链接的 `sign` 是按 `num` 算的，改了就 401。
2. **一个身份只完成一条预约**：winner 拿到号后，其余 IP 立刻停排，不再尝试拿第二个号。
3. **会话 20 分钟**：放行后别犹豫，先判号再谈别的；判到号就抓第 2 步页面，别在页面上反复刷新。
4. **失败不狂重试**：单 IP 连续 3 次 WAF 失败就停，换 IP 比重试有用。
