# 代理链路实测：巨量IP + 现有流程能不能跑通（2026-11-11 14:36–14:45）

> 结论：**能，而且比直连快 7 倍。**
> 更关键的发现：**浏览器那套放行 cookie 换 IP 照样有效**——这套系统没有把会话绑死在出口 IP 上。
> 这意味着「多 IP 并行排队 / 一个会话从任何 IP 抢业务」在技术上成立。

---

## 一、提取 API 的两个硬限制（先记住，少踩坑）

```
http://v2.api.juliangip.com/company/dynamic/getips
  ?auto_white=1&num=1&pt=1&result_type=text&split=1
  &trade_no=2977409725466488&sign=d2210aad5b296a631c2a4181b520da8c
```

| 限制 | 实测现象 | 处理 |
|---|---|---|
| **`sign` 是按 `num=1` 签的** | 把 `num` 改成 3 → 返回 `{"code":401,"msg":"签名校验失败"}` | 一次只能提 1 个；要多个就循环调 |
| **动态代理存活很短** | 几分钟后同一 IP:端口 变 `407 CONNECT tunnel failed` | 提取后**立刻**用；过期就重提 |
| 提回来的是「网关地址」，出口 IP 另算 | `222.216.120.212:50349` → 实际出口 `117.169.222.178`（China Mobile） | 别拿提取到的 IP 当出口 IP 判断 |

## 二、可用率与速度（实测）

### 单批 4 个，全部可用

```
  OK  222.216.120.186:13761  status=200  1.50s
  OK  150.139.247.206:31743  status=200  0.64s
  OK  175.6.31.244:29255     status=200  0.54s
  OK  183.131.59.246:14181   status=200  0.74s
可用代理：4/4
```

### 直连 vs 代理：第 1 步判号各打 5 次

| 模式 | 成功率 | 单次耗时 | 平均 |
|---|---|---|---|
| 直连（家宽 `14.127.169.56`） | **5/5** | 3.55 / 3.83 / 5.09 / 7.98 / 12.28 s | 6.55 s |
| 代理 `222.216.120.212:50349` → 出口 `117.169.222.178` | **5/5** | 0.87 / 0.88 / 0.89 / 0.92 / 1.01 s | **0.91 s** |

**代理快 7 倍**，而且波动小得多（家宽那条有 12 秒的抖动，代理稳定在 1 秒内）。
原因很朴素：这些是移动/电信机房到香港的直连链路，比家用宽带绕的节点少。

## 三、完整链路：代理跑通到「判号」

```
① GET  abs3/?lang=sc                                 200  （HWWAFSESID 正常下发）
② GET  abs3/SelectCountry?…                          302  （c=tdabsditest e=tdabsd261110kla）
③ POST abs4/spa-api/queue/…/enqueue                  200  queueId=158c200d-7b54-4697-b703-ffa870b6417b
④ POST …/{queueId}/status                            200  state=2 page=queue forecast=InLine
⑥ POST abs1/…/AdminServlet_tchinese?cmd=cmdGetOfficeQuotaDIAction
                                                     200  无名额=False? → 无名额=True
                                                         TrackId=20261111-144015-11-7271
```

**没有一次 412、没有一次 Restricted**——说明华为 WAF 与 Queue-it 都不按"机房/移动 IP 段"一刀切，
只要不是 Cloudflare/WARP 那类隐私中继，普通国内宽带/移动出口都能过。

> 对比一下：本机系统代理 `127.0.0.1:10809`（xray → WARP，出口 `104.28.161.13`）是被官方 FAQ Q20
> 点名的类型，预演时一点「继续」就被判 `Restricted access`。**所以要不要用代理，关键不是"代理"，
> 而是"出口是不是住宅/移动宽带段"**。

## 四、最有价值的发现：会话不绑出口 IP

同一套 15 条 cookie（含 `QueueITAccepted-SDFrts345E-V3_tdabsd261110kla` + `abs3|urltoken`），
分别从 **3 个完全不同的出口**打第 1 步：

| 出口 | 结果 |
|---|---|
| 家宽 `14.127.169.56`（直连） | 200，无名额，`TrackId=20261111-143320-11-64` |
| 移动 `117.166.192.109`（代理 A） | 200，无名额，`TrackId=20261111-143645-11-…` |
| 移动 `117.169.222.178`（代理 B） | 200，无名额，`TrackId=20261111-143822-21-…` |

三次都正常处理、都发新 TrackId。

这条推翻了 `接口直约_可行性.md` 里那句「会话与 IP 绑定，换 IP 后不硬用旧会话」——
**至少对 `abs1/abs2` 的 JSP 业务层和 Queue-it 放行票，不成立**。
（WAF 层可能仍按 IP 判挑战，但本次三个出口都没触发。）

## 五、由此得到的战术（17:00 用得上）

```
16:40  用 N 个代理各跑一遍 sniper --probe        ← 每个 IP 都拿到独立 WAF 票 + 独立 queueId
16:55  浏览器那边照常守一条主队列
17:00  多 IP 同时轮询 status，谁先出 redirectUrl 用谁
17:00+ 拿到放行的那条，把 cookie 导出 → 主机用这套 cookie
       从任意快出口（哪个代理快用哪个）并行试选时段
```

**为什么这样更快**：判号一次 0.9 秒（代理），20 分钟窗口够跑上千次；而页面点一次要 2–3 秒。
17:00 名额刷新瞬间，用来「探到哪个办事处/日期有号」的探测次数直接决定抢到概率。

代价与风险（如实写）：

| 项 | 说明 |
|---|---|
| 代理存活 | 几分钟就换，需要脚本循环重提（`runs/rev/proxy_batch.py` 已做） |
| 同一 IP 高频请求 | 建议单 IP 请求间隔 ≥1.5 s；本次 5 次/2 s 间隔未触发 412 |
| 放行票泄露面 | 同一套 cookie 多 IP 共用 = 任何一处被封都影响全部，别把票贴到外部 |

## 七、两个新踩的坑（都很浪费时间，记下来）

| 坑 | 现象 | 根因 |
|---|---|---|
| PowerShell 吞空串 | `python x.py "" 5` → `argv[1]` 变成 `"5"`，被 curl 当代理地址 → 报 `Failed to connect to 0.0.0.5 port 1080` | 参数解析错位；现在脚本把纯数字当成轮次、把 `-` 当直连 |
| curl_cffi `proxies={}` | 同样报 `0.0.0.X:1080`（X 每次不同） | 空 dict 让 libcurl 读到野指针；直连时应**不传** `proxies` 键并 `trust_env=False` |
