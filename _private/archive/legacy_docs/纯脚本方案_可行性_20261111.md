## 二、为什么说"票不能复用"这个结论不成立（必须重做实验）

`waf_replay.py` 的判读是「HIK0 与浏览器指纹绑定，浏览器拿票 → 纯 HTTP 复用不成立」，依据是全 400。
但那次实验里**两个变量同时变了**：

| 项 | 铸票时 | 回放时 |
|---|---|---|
| 浏览器内核 | Chromium **156**.0.8078.80 | — |
| 请求 UA | 浏览器真实 UA（156） | 手写 `Chrome/131` |
| TLS 画像 | Chrome 156 真实 ClientHello | `impersonate=chrome124/120/safari` |

UA 与 TLS **一起被换掉**，全 400 完全可能只是 UA 不匹配，和 JA3 半毛钱关系没有。
这在方法论上是"双因子混淆"，不能作为定论，否则会误导你上最贵的那条路（Node 硬解挑战）。

**必须做的实验：一次只动一个变量。** → `t0_bindprobe.py`

```
0 分诊   裸 GET                      → 出口是活的(412/200) 还是已死(400/000)
1 基线   票 + 铸票UA + 最近TLS       → 不是 200 后面全无意义
2 ★换TLS 票 + 铸票UA + 另一个TLS     → 200 = TLS 不绑 = 纯 HTTP 成立
3 对照   票 + 换UA + 对应TLS
4 只换UA 票 + 换UA + 原TLS           → 区分「绑UA」还是「绑UA+TLS成对」
5 减头   票 + 铸票UA + 最小头集
6 降协议 票 + 铸票UA + HTTP/1.1
```

判决树：

| 现象 | 含义 | 走哪条路 |
|---|---|---|
| `2=200` | TLS 不绑 | **R1 纯 HTTP**，最省 |
| `2=400 且 3=200` | 绑 UA+TLS 成对 | **R1'**：把铸票 UA 降到 curl_cffi 支持的主版本再铸 |
| `4=200 且 2=400` | 只绑 UA | **R1**：UA 一字不差即可 |
| `1=200` 但 2/3/4 全 400 | 三元绑定（IP+UA+TLS） | **R2 / R3** |
| `1≠200` | 票过期 / 出口死 / 票不是过挑战后的 | 先修票，别解释矩阵 |

## 三、三条路线（按性价比排序）

### R1 —— 票 + 指纹对齐（首选，真·零浏览器）

思路：**容器从浏览器换成 `curl_cffi`，但把 UA / TLS / cookie 三元组对齐到铸票那一刻。**

已补的两处工程坑（本次改动）：

1. `token_pool.MintWorker` 新增 `--engine patchright`：**headless 也能铸票**（你实测 patchright headless 412→200，1.9s；原版 playwright headless 挑战 JS 直接 400）。
2. `MintWorker.default_ua()`：铸票 UA 由内核主版本自动生成（156），
   不再用手写的 `DEFAULT_UA`（131）。**票里 UA-CH 报 156、UA 头写 131，这种自相矛盾本身就是异常特征**，
   也是上次复现 400 最可能的真凶。

命令：

```powershell
# 铸票（无窗口，脚本自跑，无人参与）
python token_pool.py --selftest --engine patchright          # 先自检（零网络）
python token_pool.py --warm --direct --headless --engine patchright   # 本机出口铸一张

# 验证绑定维度（7 次请求，5 分钟，一次性）
python t0_bindprobe.py --ticket runs/rev/browser_cookies.json --proxy ""

# 通过后：全链纯 HTTP
python sniper.py --cookies runs/browser_cookies.json --step1
```

### R2 —— 无窗口内核（已实测可行，只是"起了个进程"）

如果你对"不开浏览器"的定义是**不弹窗、不用手点**，这条路今天就能跑完：
patchright headless 过挑战 → 就在这个无窗口上下文里同源 `fetch` 跑完 enqueue/status/业务页。
`waf_flow_abs4.py` 已经是这个形态，缺的只是把它接成状态机而不是 demo。

代价：一个 Chromium 进程约 300–400 MB（`mem_probe.py` 可测）；4 个工人 = 1.5 GB 左右，串行最省。
收益：**不依赖任何算法逆推**，WAF 升级也不怕。

### R3 —— Node 里跑挑战 JS（真·零进程，成本最高）

`waf_solve.js` 失败的原因是**方法错**，不是不可行：

| 错法 | 为什么必炸 |
|---|---|
| 用 `Proxy` 万能 stub 伪装 DOM | 挑战 JS 会 `typeof`/`instanceof`/`toString` 全量探测，stub 处处返回真值 → 分支暴涨 → 4 GB OOM |
| 直接 `vm.runInContext` 跑混淆体 | 挑战脚本带反调试（`debugger` 循环 / 栈检查 / 时间差），Node 默认能进死循环 |
| 只喂 `window/document` | 它还要 `navigator`、`screen`、`canvas`、`WebGL`、`AudioContext`、`Intl` 时区、字体 |

正确姿势（如果 R1 判决失败才上）：

```
jsdom（真 DOM/真 getter）+ 固定 canvas/WebGL 指纹 + 关掉 debugger 陷阱
（--inspect=0、patch Function.prototype.toString、Error.prepareStackTrace）
+ 真 HTTP 发验证请求，把 Set-Cookie 的 HIK0 收回 → 一张票 50–150ms
```

判断标准很简单：**R3 一分钟能出 400 张票，R2 一分钟出 20 张**。只有需要 100 IP 时才值得写。

### 6.2 实测量出来的两个真问题（都已修）

**① `sniper.py` 的节流闸门从来没接上。**
`_gate()` 与 `_get/_post` 都调 `self.th.wait()`，但 `__init__` 里从没赋值 → 第一次请求必
`AttributeError: 'Sniper' object has no attribute 'th'`。这是上次接 throttle 时漏的，
意味着「3s 间隔 / 连续 412 熔断」这套红线此前**一条都没生效**。已补，并把 `min_interval` 做成参数。

**② headless 的 UA 是 `HeadlessChrome`，UA-CH 是空 `{}`。**
`_ua_probe.py` 实测（同内核 156.0.8078.80）：

| 启动方式 | UA | Headless 标记 | window vs screen |
|---|---|---|---|
| `headless=True` | `HeadlessChrome/156` | ❌ 有 | 全相等（假） |
| `headless=False + --headless=new` | `HeadlessChrome/156` | ❌ 有 | 全相等（假） |
| **`headless=False`（窗口移到屏幕外）** | **`Chrome/156.0.0.0`** | ✅ 无 | 1382×856 vs 1366×768（真） |

所以 `mint_align.py` 默认走**有窗口 + `--window-position=-32000,-32000`**：
不弹到眼前、不抢焦点，但身份是真的。拿 `HeadlessChrome` 铸出来的票，
R1 会把这个假 UA 原样重放到业务层——等于自己给自己留了个特征。

### 6.3 离线验证（`python _selftest_align.py`，已通过）

```
✅ UA 逐字一致          ✅ sec-ch-ua 逐字一致      ✅ accept 逐字一致
✅ cookie 来自 jar      ✅ 伪 cookie 头被丢        ✅ host 由 curl 决定
✅ XHR accept 已切换    ✅ XHR 仍带原 UA           ✅ 跨源 Referer 被拦
✅ 同源 Referer 照发    ✅ Sniper 接管不炸         ✅ 节流闸门就位
```

其中三条是这次才第一次被验证的工程规则：

- **XHR 头不能沿用导航头**：`/spa-api/` 自动切 `Accept: application/json, text/plain, */*`，
  `Sec-Fetch-*` 由 `document/navigate/none` 改成 `empty/cors/same-origin`（由导航头确定性派生，
  不额外多打请求去采）。
- **跨源 Referer 一律不发**：实测过 `Referer: https://abs1.td.gov.hk/` 打 abs3 → 400 被判非法。
- **疑似幻头必须丢**：`host` / `cookie` / `content-length` / `accept-encoding` 交给 curl 自己管，
  历史上这些手写值正是 400 的常见来源。

`--probe` 的判读（与 T0 实验同一套树）：

| 结果 | 含义 | 下一步 |
|---|---|---|
| `chrome136 200` | TLS 不绑，纯 HTTP 成立 | 直接 ③ |
| `全 400` | 出口 IP + UA + TLS 三元绑定 | 换出口重铸；或退 R2 取票 |
| `412` | 票不是过挑战后的会话 / 已过期 | 重铸，别换画像白烧配额 |

### 6.5 已知边界（写清楚，不糊）

- **TLS 无法 1:1 对齐**：铸票内核 156，curl_cffi 最高 `chrome136`。R1 是「同族最近画像」，
  不是同一个 ClientHello。票龄 >25 分钟会主动提醒（TTL≈30min，换 IP 立即作废）。
- **`sec-fetch-*` 是推断项**：Playwright 的 `request.headers` 不暴露它们，默认不补；
  真排查 400 时用 `--synth-secfetch` 做 A/B，别默认打开（幻头比缺头更容易被判非法）。
- **一张票只能一个出口**：票与出口绑定，`--proxy` 必须与铸票时一致。

### 6.7 铸票前置分诊闸（`--before-mint`，已接线并实测）

**它拦的正是 16:30 那个剧本**：出口已经被打 → 铸票器照样启动浏览器 → `goto` 抛 SSL 错 →
仍把半死 cookie 写成一张票 → `probe` 再花 3 次请求 → 全 400。
代价不是 3 秒，是**把一个已经被打的出口又摸了 4 次**，而黑名单越摸越深。

现在：**先分诊 1 次 → 判活才启动浏览器**。

| 判定 | 触发条件 | 闸门 |
|---|---|---|
| `OK` | 200 / 302 | ✅ 放行（裸 HTTP 就能打，票可选） |
| `CHALLENGE` | 412 且 body 含 `$_ts`/`nsd=` | ✅ 放行（**这正是需要铸票的时候**） |
| `BANNED` | 400（空 body / 被判非法） | ⛔ 拦下，换出口 |
| `DROP` | 超时 28 / RST 56 / 连不上 7 / TLS reset | ⛔ 拦下，换出口 |
| `TLS_WRONG` | `WRONG_VERSION_NUMBER` | ⛔ 拦下（代理不支持 CONNECT / scheme 写错） |
| `TLS_CERT` | 证书链问题 | ⛔ 拦下（通道其实是通的，需单独处理） |
| `GATEWAY` | 502/503/504 | ⛔ 拦下（多半是代理侧） |

**实测（23:05）**

```
# 真出口
✅ OK  HTTP=200 len=708 1050ms  站点不挑战，裸 HTTP 就能打，票可选
   → 放行，继续铸票，分诊结果写进票的 preflight 字段

# 死出口 http://127.0.0.1:9
❌ DROP  HTTP=— 2051ms  连不上（7）：端口关或代理死
   → 拦住，不启动浏览器、不发后续请求
   耗时 2183ms    chrome 进程 前=20 后=20      ← 一个都没起
```

| 命令 | 行为 |

| `mint_align.py` | 默认开；`--no-before-mint` 可关；拦截时退出码 **44** |
| `proxies_fetch.py --triage` | 每代理额外对目标站分诊 1 次，筛掉「能上百度但被目标 WAF 打死」的出口 |

注意：分诊本身也花 1 次目标访问，所以**只在铸票前做**，别在批量循环里无脑开。

### 6.8 412 挑战离线复放（`_drill_412.py`）—— 挖出两个真结论

零目标访问：把 11-11 存下的 412 页面 + 304KB 挑战 JS 在本地还原（`127.0.0.1` 起服务，
`<script src>` 改指本地副本），让真内核去跑，看它能不能执行完。

**结论一：内核有完整执行能力**

成功的那次（3.21s）：

```
首帧  ts_type=undefined  n_scripts=0           ← 页面已被挑战 JS 整体重写
cookie= HIK0kat3rt9xP=auOsrm0-sG6MgLsSxq2kPVQ...   492 字符
随后导航 → /tdabs/cloud/schinese/maintenance.htm
```

- 无卡死、无 pageerror、JS 堆峰值 5.2 MB（`waf_solve.js` 那次是 4 GB OOM）
- 令牌长度见过 **343** 和 **492** 两档
- 挑战完成后页面被整体重写并导航到业务页/维护页——这解释了真站上"过完挑战后拿到的 HTML"是什么形态

**结论二（更重要）：cookie 后缀是 `P`，不是 `O`**

| 名字 | 观测 | 长度 |
|---|---|---|
| `HIK0kat3rt9xO` | 早期抓到的短令牌 | 109 |
| **`HIK0kat3rt9xP`** | **本次复放实测**；`waf_enter.py`/`run_guard.py` 也检测的是它 | **343 / 492** |
| `enable_HIK0kat3rt9x` | 开关标记，不是令牌 | — |

`runs/session_form_noquota_w1_171304.json` 里 **两者并存**，说明服务端按状态/轮次下发不同后缀。

**这是个静默误杀型 bug**：`mint_align.py` 原本写死 `HIK0kat3rt9xO`。真站一旦下发 `P`，
等 cookie 的循环会一直等到 20s 超时，然后把一张**已经铸好的票**判成「挑战没跑完」退出码 41。

已修（统一口径，认前缀不认后缀）：

| 文件 | 改动 |
|---|---|
| `waf_cookies.py` | **新增**。`is_hik0 / has_hik0 / find_hik0 / strength`，唯一判定口径 |
| `mint_align.py` | 3 处写死 → `find_hik0(names)`；票里新增 `hik0_names` 字段 |
| `token_pool.py` | `_has_hik0()` 包装；`WAF_COOKIES` 去掉写死项 |

**复放的成功率必须说清楚**：抽样 11 次，成功 3 次（约 1/4~1/3）。
失败时页面停在 `ready=loading`、`chall.js` 未执行完——因为本地没有服务端会话种子，
挑战 JS 的时序/会话门槛过不去。

**所以：这次复放能证明「内核有能力跑完」，但不能当作 17:00 的可靠性判据。**
真正的判据只有一个——明天 16:30 之后，首包 412 时铸票，看票里有没有 `HIK0kat3rt9x*`。
