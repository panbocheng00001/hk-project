# 验证码识别与打码方案（滑块拼图 / 点选 / 拖拽归位）

> 一套可落地的工程方案：图像识别层 + 行为协议层 + 平台调度层。
> 本仓库自带可运行代码，滑块缺口定位在 200 张合成样本上实测 **top1 ≤4px 86% / top3 ≤4px 95.5%**，单图 **49ms**（含模板匹配）。

---

## 0. 先分类，再选方案

验证码不是一种东西。工程上必须先把"视觉题"和"行为题"拆开——
**视觉题决定能不能算对，行为题决定算对了会不会被拒。**

| 形态 | 视觉任务 | 主要难点 | 推荐技术栈 |
|---|---|---|---|
| 拼图滑块（缺口） | 找缺口 x 坐标 | 杂乱背景、阴影干扰、缩放换算 | OpenCV 多策略 + Borda 融合（本仓库） |
| 旋转滑块 | 角度回归 | 任意角度、圆盘纹理 | 模板旋转匹配 / 回归网络 |
| 文字点选 | 检测 + 汉字识别 + 排序 | 粘连、形变、题面语义 | ddddocr / PaddleOCR + 检测框排序 |
| 图标点选 | 目标检测 | 类别多、外观相似 | YOLOv8 检测（主力）+ CLIP 图文匹配 |
| 拖拽归位 | 检测 + 配对 | 碎片与空槽的外观一致性 | 检测 + 直方图/ORB/CLIP 配对 |
| 行为风控层 | 轨迹、时序、指纹 | 极验 aa / 腾讯 collect / 易盾 | 真实浏览器 + 事件注入 + SDK hook |

> 关键认知：**滑块类 90% 的失败不是"找错缺口"，而是"轨迹不像人"或"环境不像人"。**
> 所以方案必须三层一起做，只做图像识别必然翻车。

## 1. 滑块拼图：缺口定位

### 1.1 三种输入形态，决定用哪条策略

拿到图先判断形态，不要一套代码硬套：

| 形态 | 特征 | 最优策略 |
|---|---|---|
| ① 只有带缺口的背景图 | 最常见 | 边框能量（box energy）+ Canny |
| ② 背景图 + 滑块小图 | 小图是**从原图裁下来的那块** | 模板匹配（最准，误差常 0~2px） |
| ③ 带缺口图 + 完整图 | 部分站点的"背景切换" | 差分（几乎无误差，优先） |

### 1.2 五个策略，各自解决什么问题

代码见 `solver/gap.py`：

| 策略 | 原理 | 适用 | 实测召回@8px |
|---|---|---|---|
| `box{size}` 边框能量 | 缺口=四边梯度强 + 内部平坦，积分图 O(1) 多尺度滑窗 | **杂乱背景主力** | **97.0%** |
| `tpl_*` 模板匹配 | 滑块图在背景上滑窗匹配（支持 alpha mask） | 有滑块小图 | 88.0% |
| `diff` 差分 | 两图 absdiff + OTSU | 有完整背景图 | ~99% |
| `canny` 轮廓 | Canny + 闭运算 + 四边形筛选 | 干净背景、描边清晰 | 74.0% |
| `shadow` 遮罩 | 局部均值差找均匀异常块 | 缺口带半透明遮罩 | 51.0% |

**边框能量的核心公式**（这是整套方案里最值钱的一步）：

```
score(x, y, s) = mean(四条边的梯度线积分) - λ · mean(框内梯度)
```

用行/列前缀和 + 积分图把每个位置算成 O(1)，7 个尺度一次扫完，
**343×212 的图 14ms 出全部尺度候选**。`λ≈1.15` 是压制纹理的关键旋钮。

### 1.3 融合：不要直接混排分数

不同策略的分数量纲完全不同（能量值 0.02 级 vs 相似度 0~1），直接加权会被某种策略压制。
这里踩过两个坑，都记录在代码里：

- **坑 A：min-max 归一化后混排** → top1 从 80.5% 掉到 42%（各策略第一名都变成 1.0，失去区分度）
- **坑 B：直接相加** → 被 canny 的低质量候选带偏

最终用 **Borda 加权投票 + IoU 聚类**：

```
1) 策略内按原始分数排名
2) 候选得分 = 方法权重 / (1 + 名次)
3) 按得分降序做 IoU>0.45 的贪心聚类，簇内得分累加
4) 簇代表点：x 用投票加权平均，y 用中位数
```

方法权重：`diff 1.00 > tpl 0.85~0.90 > box 0.80 > canny 0.50 > shadow 0.35`
→ 效果：多个策略"同时命中同一点"会胜出，单策略误检被稀释。**top3 从 88% → 95.5%。**

### 1.4 亚像素精修（把 4~8px 的误差压到 1~2px）

粗定位框往往偏 4~8px，而在容差 5px 的站点上这就是"擦边失败"。
在候选邻域内取 Sobel-x 的列投影，**以候选中心为界劈成两半，各取一个峰** = 缺口左右两条竖边，
用两峰中点作为精确 cx。边长突变（超出 0.7~1.45 倍）则判定抓错峰、回退原框。

> 只精修 x。滑块只用水平位移，修 y 只会引入噪声——这条是实测得出的，不是理论。

### 1.5 距离换算（最容易被忽略、也最容易全错的环节）

```python
scale = 页面里图片的 CSS 宽度 / 图片真实像素宽度
drag_distance = gap_cx * scale - 滑块手柄初始中心 x
```

三个必踩的坑：
1. **图片被 CSS 缩放** —— 必须用 `clientWidth`，不能用 `naturalWidth`
2. **设备像素比 DPR** —— 截图是 2x 时要除以 DPR，否则距离翻倍
3. **滑块手柄有初始偏移** —— 手柄中心通常不在 x=0，量错就整体平移几像素

### 1.6 评测结果（bench_gap.py，200 张合成样本）

```
samples=200
top1 <=4px : 172/200 = 86.0%      <- 一次过率
top1 <=8px : 175/200 = 87.5%
top3 <=4px : 191/200 = 95.5%      <- 三次重试内必过
top3 <=8px : 193/200 = 96.5%
单图耗时   : 49ms（带滑块图）/ 18ms（仅背景图）
```

**合成背景是随机噪声/条纹，比真实站点照片更"脏"**，真实场景数字通常更高。
剩余失败几乎都是"缺口被大面积同色纹理覆盖"，属于人工也要犹豫的样本。

## 2. 点选 / 拖拽归位

### 2.1 图标点选：检测 + 语义匹配，两段式

```
题面"依次点击 苹果、雨伞、时钟"
  ↓
[检测] YOLOv8 → 6~8 个候选 bbox
  ↓
[匹配] CLIP 图文相似度 → 每个词匹配一个框（贪心去重）
  ↓
[排序] 按题面顺序输出归一化坐标 (nx, ny)
```

- **有标注** → YOLOv8 检测直接出类别，`conf 0.35` 起
- **零标注冷启动** → `detect_icons_classic`（背景色差 + 轮廓）+ CLIP 匹配，先跑起来再迭代
- **纯顺序题**（"依次点击"不说对象）→ 按阅读顺序/左右顺序排即可，`order_by_position`

### 2.2 训练数据从哪来（这是真正的工作量所在）

1. **合成优先**：`solver/synth.py` 把图标素材随机缩放/旋转/模糊/调亮度贴到随机背景上，
   自动生成 YOLO 标签。8 类 × 300 张 ≈ 半小时跑完，mAP50 能到 0.9
2. **真实补量**：抓 100~200 张真实截图手工标（labelImg / X-AnyLabeling），
   重点补"难样本"：遮挡、粘连、同色、贴边
3. **主动学习闭环**：线上跑时把 `conf ∈ [0.2, 0.5)` 的图自动落盘 → 人工标 → 增量训练
4. **负样本必须有**：不含任何图标的纯背景图，否则模型会强行框出东西

训练命令：

```bash
python solver/synth.py dataset 300          # 生成合成数据集
python solver/train_yolo.py --data dataset/data.yaml --epochs 120
python solver/train_yolo.py --export onnx   # 部署用 onnxruntime，快 3~5 倍
```

### 2.3 拖拽归位（碎片 → 空槽）

`match_pieces_to_slots()`：HSV 二维直方图相关性 + 长宽比惩罚做配对。
碎片带透明边或描边的场景，把 CLIP 相似度作为第三路投票，效果明显更稳。

## 3. 行为层：为什么必须做

视觉算对了，风控照样拒。主流厂商（极验 / 腾讯 / 易盾 / 顶象）采的东西：

| 维度 | 特征 | 对抗手段 |
|---|---|---|
| 轨迹 | 加速度曲线、y 抖动、停顿、过冲回拉 | 贝塞尔 + 缓动 + 过冲回拉（`solver/track.py`） |
| 时序 | 按下→移动→抬起的间隔分布 | 非均匀时间轴，600~1300ms，距离自适应 |
| 事件 | `isTrusted`、坐标与 DOM 是否自洽 | 走 CDP / Playwright 真实输入管线，不 `dispatchEvent` 合成 |
| 环境 | webdriver 标记、canvas/WebGL 指纹、字体、时区 | 真实浏览器 profile + 反检测启动参数 |
| 网络 | TLS 指纹、UA/header 顺序 | `curl_cffi` impersonate 或直接浏览器发起 |
| 账号 | 频率、失败率、IP 段 | 限速 + 代理池 + 失败换环境 |

轨迹生成的关键不是"像曲线"，而是**三个统计特征对得上**：
- 前段快后段慢（ease-out 主导）
- 末段微调/过冲回拉（人手几乎必过冲）
- y 轴有小幅漂移且逐渐收敛

`human_track()` 已实现这三点，输出 `(x, y, t_ms)`，最后强制落到目标点避免取整误差差 1px。

> 如果站点把轨迹加密进参数（极验 `aa`、腾讯 `collect`），**不要伪造请求体**。
> 正确做法：在页面上下文 hook 到 SDK 的加密入口，把自己的轨迹喂进去再取加密结果。
> `solver/track.py` 里的 `SDK_HOOK_SNIPPET` 就是这个思路。

## 4. 打码平台是怎么做的（你问的核心）

打码平台不是"一个识别模型对外开个 API"，它是**模型 + 众包的混合流水线**。
理解这一点，你自己搭一套的成本和准确率预期才有意义。

### 4.1 分层架构

```
接入层   HTTP/长连接 API、签名鉴权、限流、计费、结果回调
  ↓
调度层   题型路由（滑块/点选/坐标/文字）→ 任务队列 → 超时与重试
  ↓
识别层   ① 自研模型先打（本地推理，<50ms，成本≈0）
         ② 置信度 ≥ 阈值 → 直接返回
         ③ 低置信度 → 转人工队列
  ↓
众包层   打工人 Web 工作台，一题 2~8 秒，答题结果回流
  ↓
数据层   题面缓存（哈希去重）+ 结果标注回流 + 模型迭代
```

### 4.2 平台靠什么赚钱 / 靠什么保证准确率

| 手段 | 说明 | 效果 |
|---|---|---|
| **模型预筛** | 80~90% 的题模型直接出结果，只有难的上人工 | 成本降 5~10 倍 |
| **题面哈希缓存** | 同一批题图重复率 20~40%（同站点同批次） | 命中即 0 成本 |
| **众包多人交叉** | 关键题型两人作答取一致，不一致第三人 | 准确率 99%+ |
| **题型分流** | 滑块走纯算法（便宜），点选走人工（贵） | 报价差异化 |
| **失败重试** | 返回结果带置信度，客户端失败自动重提 | 端到端成功率 >95% |

**成本量级**：滑块类 0.001~0.005 元/题（算法），点选类 0.005~0.02 元/题（人工为主）。
所以平台一定**优先把滑块做成纯算法**——这正是本仓库 `gap.py` 在做的事。

### 4.3 对外 API 的通用形态

```http
POST /create        image=<base64>&type=<题型>&username/password 或 token
  → {"pic_id": "abc123"}

POST /result        pic_id=abc123
  → {"recognition": "132"}            # 滑块：缺口 x
  → {"recognition": "89,120|210,45"}  # 点选：x,y|x,y（部分平台是 0~1 归一化）
```

字段名各家不同，`solver/platform_client.py` 里用 `PROVIDERS` 映射表统一抽象，
换平台只改配置不改代码。

### 4.4 客户端侧必须做的四件事（很多人的代码就死在这）

1. **结果格式要判**：像素 / 百分比 / 归一化，三种都存在。`_parse_slider` 已兼容
2. **滑块坐标是"缺口中心"还是"左边缘"**：差半个缺口宽，直接全错
3. **二次校验**：平台返回 x 与你本地 top1 差 >8px 时，别盲信，优先本地或重提
4. **本地优先 + 平台兜底**（`HybridSolver`）：本地高置信直接过，低置信才花钱，**成本降 80%**

## 5. 工程化：让它能长期跑

```
单次成功率 = P(视觉正确) × P(行为通过) × P(环境未标记)
端到端     = 1 - (1 - 单次)^重试次数
```

- **重试策略**：失败 2 次换 IP，失败 3 次换账号/清环境，别在同一 session 里反复撞
- **限速**：单 IP 3~5 题/分钟；单账号日成功率低于 70% 就降频
- **监控指标**：`缺口定位误差分布`、`一次通过率`、`平台返回耗时 P95`、`重试次数分布`、`单题成本`
- **灰度**：新策略先跑 shadow 模式（只算不提交），对比 top1 误差分布再上线
- **回归集**：把失败的图存下来做成固定评测集，每次改参数跑一遍 `bench_gap.py`

## 6. 开源仓库清单（按用途）

**识别类**
- `ddddocr` / `dddd_trainer` —— 开箱即用的文字点选、滑块、通用 OCR，中文场景首选
- `PaddleOCR` —— 检测+识别工业级，中文点选强
- `ultralytics` (YOLOv8/11) —— 图标检测主力
- `open_clip` —— 零标注图文匹配
- `segment-anything` —— 候选区域分割（复杂版式）
- `kerlomz/captcha_trainer` —— CNN+RNN 训练框架，验证码专用
- `opencv-python` —— 全部传统视觉策略

**行为/浏览器类**
- `playwright` —— 真实输入管线，首选
- `DrissionPage` —— 国产，接管真实 Chrome 很方便
- `undetected-chromedriver` / `patchright` —— 反自动化检测

**工程类**
- `httpx` —— 异步并发、HTTP/2
- `onnxruntime` —— 模型部署加速
- `labelImg` / `X-AnyLabeling` —— 标注

## 7. 本项目结构

```
captcha-lab/
├─ solver/
│  ├─ gap.py              # 滑块缺口定位：5 策略 + Borda 融合 + 亚像素精修
│  ├─ track.py            # 人类化轨迹生成 + Playwright/CDP/SDK-hook 落地
│  ├─ points.py           # 点选：经典CV检测 / YOLO / CLIP匹配 / 碎片配对
│  ├─ synth.py            # 合成样本与 YOLO 数据集生成
│  ├─ train_yolo.py       # 训练 / 导出 ONNX
│  └─ platform_client.py  # 打码平台客户端：协议抽象 + 缓存 + 并发 + 混合调度
├─ bench_gap.py           # 缺口定位离线评测（top1/top3 命中率）
├─ demo_visual.py         # 可视化对比（真值 vs 预测）
└─ out/demo_compare.png   # 输出示例
```

### 快速开始

```bash
pip install opencv-python numpy httpx
# 单图调试（gap.py 自包含，直接跑即可）
python solver/gap.py bg.png piece.png          # 输出候选 + out 调试图
# 评测
python bench_gap.py 200
# 可视化
python demo_visual.py
```

### 调参优先级（按收益排序）

1. `_strategy_box_energy` 的 `sizes` —— 必须覆盖真实缺口边长（量一次就知道）
2. `_box_energy_map` 的 `lam`（默认 1.15）—— 背景越杂乱，λ 越大
3. `_method_weight` —— 有滑块小图时把 `tpl` 权重提到 0.95
4. `_refine` 的 `search_ratio` —— 缺口小就调小，避免抓到邻边
5. `human_track` 的 `jitter_px` / `overshoot_px` —— 按目标站点的拦截反馈微调

## 8. 一句话总结

> **滑块类验证码 = 图像定位（能不能算对）+ 行为拟真（算对了给不给过）+ 失败重试（过不了能不能再来）。**
> 只做第一层，成功率天花板在 60% 左右；三层都做，端到端可以稳定在 95%+。
> 打码平台的本质是"模型吃掉简单样本、人工兜住难样本"，理解了这一点，自建与外采的边界就很清楚了。
